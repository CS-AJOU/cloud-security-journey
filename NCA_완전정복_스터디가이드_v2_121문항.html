☁️ SECTION 01

클라우드 기초 개념 & NCP 플랫폼 개요

NCA 시험의 가장 기본적인 파트. 플랫폼 구조, 리전, 서비스 카테고리를 이해하자.

🎯 왜 중요한가

  • 시험 전반에 깔린 기초 지식
  • 리전/존 구조는 다른 서비스 이해에 필수
  • 서비스 카테고리 암기 문제 자주 출제
  • NCP 고유 상품명 vs AWS/GCP 구분

📌 중점 공부 포인트

  • 리전 목록 암기 (어떤 나라/도시인지)
  • 전문화된 클라우드 3종 암기
  • AWS 상품명과 혼동 주의
  • CLI 명령어 이름 (ncloud)
  • CAPEX/OPEX 개념

📚 공부 방법

NCP 공식 문서의 제품 카테고리를 먼저 훑어보면서 어떤 상품이 어느 카테고리에 속하는지 큰 그림을 잡아. AWS를 알고 있다면 대응 관계를 매핑해보면 효과적이야.

핵심 개념 & 용어
리전 (Region)

한국(KR), 미국 서부(US-West), 일본(JP), 홍콩(HK), 싱가포르(SG), 독일(DE). 미국 동부(US-East)는 없음!

전문화된 클라우드

민간, 금융, 공공 3종. 아카데미 없음!

Outpost vs NCP

Outpost = AWS 상품. NCP 유사 서비스 = Neurocloud

CLI 명령어

NCP 터미널 관리 명령어 = ncloud

서비스 카테고리 예시

Cloud Hadoop → Analytics / VMware on Ncloud → Hybrid & Private Cloud / SSL VPN → Security

CAPEX vs OPEX

클라우드 = OPEX(운영비용) 모델. 레거시 = CAPEX(자본적 지출) 모델

🖥️ SECTION 02

Compute / Server

서버 타입, 스펙, 운영 방법, Init Script까지 — 실제 클라우드 운영에서 가장 기본이 되는 파트.

🎯 왜 중요한가

  • 출제 비중이 가장 높은 파트 중 하나
  • 서버 정지 필요/불필요 케이스 암기 필수
  • 서버 타입별 차이점(베어메탈, GPU, 마이크로)
  • Init Script 명령어 (-y, enable)

📌 중점 공부 포인트

  • 서버 정지 필요 vs 불필요 작업 구분
  • 베어메탈 RAID 옵션 (1가지가 아님)
  • 마이크로서버 지원 OS (Windows 없음)
  • GPU 최대 개수·정지 시 요금
  • 서버 타입별 CPU:RAM 비율

📚 공부 방법

서버 관련 문제는 숫자(최대 개수, 용량)와 예외 케이스(정지 불필요한 작업, 지원 안 되는 OS)가 함정이야. 표로 정리해서 비교하며 외우는 게 가장 효과적.

핵심 개념 & 용어
서버 정지 불필요

이미지 생성, 스냅샷, 공인IP 부여. 스펙 변경·반납은 정지 필요

Init Script

자동화 설치: yum install -y (-y 필수!). 자동 시작: systemctl enable. PHP 미지원.

서버 타입 RAM 비율

Standard 1:4 / High-CPU 1:2 / High-Memory 1:8

마이크로서버

1vCPU/1GB. OS: CentOS/Ubuntu만 (Windows 없음!). 1년 무료.

GPU 서버

최대 4개/VM. 제공: P40, T4, V100. 정지해도 요금 발생!

베어메탈 RAID

RAID 1/5/10 선택 가능 (RAID 1만 X). Oracle Linux 지원.

✓ 정답: 2번

Data Teleporter 기본 대여 기간은 30일. 60일이 아니야.

▾

3) 리눅스 서버에서 공유 가능한 CIFS 프로토콜을 제공한다.
4) NAS 생성 시 마운트포인트 정보를 제공한다.
✓ 정답: 3번

Linux = NFS 프로토콜, Windows = CIFS 프로토콜. 리눅스에서 CIFS를 쓴다는 건 틀린 설명.

💡 NFS = Network File System = Linux. CIFS = Common Internet File System = Windows.

4) LB에서 발급된 CNAME을 ROOT DOMAIN에 등록 가능
✓ 정답: 4번

DNS 표준상 Root Domain(apex domain, 예: ncloud.com)에는 CNAME 레코드를 등록할 수 없어.

▾
1) 애플리케이션 로드밸런서
2) 네트워크 로드밸런서
3) 네트워크 프록시 로드밸런서
4) 애플리케이션 프록시 로드밸런서
✓ 정답: 3번

네트워크 프록시 LB는 TCP 기반 세션 유지가 필요한 애플리케이션에 최적.

101
네트워크 로드밸런서의 특징으로 틀린 것은?
▾
1) 별도의 설정 없이 Client IP 확인이 가능하다.
2) 분배 알고리즘은 Source IP Hash와 Round Robin 방식만 제공한다.
3) 로드밸런서를 사용하기 위해 서버에 별도의 설정이 필요하다.
4) HTTP, HTTPS 프로토콜을 지원하지 않는다.
✓ 정답: 3번

네트워크 로드밸런서는 투명한 연결을 지향하며, 서버 측에 별도의 추가 설정이 필요 없어.

103
Classic 환경 로드밸런서와 유사한 VPC 환경에서의 로드밸런서는?
▾
1) 애플리케이션 로드밸런서
2) 네트워크 로드밸런서
3) 네트워크 프록시 로드밸런서
4) 애플리케이션 프록시 로드밸런서
✓ 정답: 3번

클래식의 Proxy 기반 LB와 기술적으로 가장 유사한 VPC 상품은 네트워크 프록시 로드밸런서.

▾

2) VPC 환경에서는 3가지의 로드밸런서가 제공된다.
3) 부하처리 성능에 따라 Small/Medium/Large 중 스펙을 선택할 수 있다.
4) Proxy 방식의 로드밸런서를 사용하면, 별도의 설정없인 클라이언트의 IP를 확인할 수 없다.
✓ 정답: 4번

Proxy 방식(ALB, NPLB) 로드밸런서는 클라이언트 IP를 확인하기 위해 XFF 헤더 등 별도 설정이 반드시 필요해.

💡 4번은 맞는 설명이야. 즉 '별도 설정 없이는 불가능하다'가 맞는 말이므로, 이게 틀린 보기로 출제된 게 아님. 문제를 잘 읽어봐!

4) Access Log: CDN 사용 로그를 확인할 수 있는 기능

Ignore Query String은 URL 쿼리스트링을 무시하고 캐싱 효율을 높이는 설정이야. 참조 방지는 Referrer Domain 설정의 기능.

✓ 정답: 2번

데이터 전송량 요금은 '일 평균'이 아니라 '월간 총 전송량'과 '요청 수'를 합산하여 청구돼.

CDN+ 설명 중 틀린 것은?
▾
1) CDN+는 HTTP/HTTPS 프로토콜을 통해 다양한 원본 서버와의 콘텐츠 연동을 지원합니다.
2) 원본 서버로 고객이 보유 중인 다양한 웹 서버 및 NCP의 Storage, Server를 선택할 수 있습니다.
3) HTTPS로 웹 서비스를 제공하는 경우 콘텐츠가 HTTP로 호출되면 서비스가 불가능합니다.
4) 레퍼러로 등록된 도메인 기준 접근 허용 기능을 제공합니다.
✓ 정답: 3번

HTTPS로 서비스 중이라도 HTTP 호출을 허용하도록 설정하면 서비스 이용이 가능해.

108

▾

2) Ignore Query String: CDN 서비스가 원본 서버에 요청할 때 URL에 포함된 GET 파라미터를 제거한 후 요청
3) Referrer Domain: 콘텐츠가 지정된 도메인에만 제공되게 하여 다른 사이트에서 참조되는 것을 방지
4) Cache Expiry: 사용자 요청에 의해 요구되는 콘텐츠를 빠르게 제공하기 위해 캐시 서버에 저장
✓ 정답: 4번

빠르게 처리하기 위해 데이터를 저장하는 것은 Caching이며, Expiry는 그 데이터의 유효 기간이야.

💡 Cache Expiry = 캐시 만료 시간. 저장하는 행위는 Caching.

📈 SECTION 06

Auto Scaling

ASG와 Launch Configuration의 역할 분리, 쿨다운 개념 — 구조를 이해하면 쉬워!

🎯 왜 중요한가

  • LC vs ASG 역할 분리가 핵심
  • 쿨다운 개념 이해
  • ASG 구성 항목 vs LC 구성 항목

📌 중점 공부 포인트

  • OS 설정은 LC에서! ASG에서 X
  • 쿨다운 = Init Script 실행 대기 기간
  • ASG 설정: LB, ACG, VPC/Subnet, 정책, 일정
  • NAS는 AS 구성 항목이 아님
  • 헬스체크: 서버+LB (네트워크 트래픽 X)

📚 공부 방법

LC=레시피(어떤 서버를 만들지), ASG=공장(얼마나 언제 만들지)로 기억해. 각각에서 설정하는 항목이 다른 것이 포인트야.

Auto Scaling 구성 요소

Launch Configuration (LC)

  • 서버의 OS, 스펙, 이미지, Init Script 정의
  • 로드밸런서는 LC가 아닌 ASG에서 설정!
  • 내 서버 이미지 사용 가능

Auto Scaling Group (ASG)

  • LC를 가져와서 정책/일정/LB/ACG 관리
  • 최소/기대/최대 용량 설정
  • 헬스체크: 서버 상태 + LB 응답
관련 기출문제 해설 5문항

2) 오토스케일링에서 사용할 Launch Configuration
3) 서버 증가, 감소 정책
4) 일정 설정
✓ 정답: 1번

서버의 OS와 사양은 Launch Configuration(LC)에서 정의해. ASG는 LC를 가져와서 언제/얼마나 늘릴지 관리만 해.

💡 LC = 레시피(어떤 서버를 만들지), ASG = 공장(얼마나, 언제 만들지)

▾

✓ 정답: 4번

LC는 서버의 OS, 스펙, 스크립트를 설정하며, 로드밸런서는 ASG 단계에서 연결해.

💡 LC = 서버 설정(OS/이미지/스크립트), ASG = 인프라 연결(LB/ACG/VPC)

2) 헬스체크
3) 기대용량
4) Policy

쿨다운(Cooldown): 새 서버 생성 후 Init Script 실행, 패키지 설치 등 준비 시간 동안 또 다른 스케일링이 일어나지 않도록 대기하는 기간.
